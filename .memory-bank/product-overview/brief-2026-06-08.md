# Figma Plugin + Agent-Reviewer · brief for the agent consilium

**Date:** 2026-06-08
**Context:** Effective.dev × Ony (partner design studio) agreeing on the Figma → Dev handoff process.
**Purpose of this document:** give the agent consilium a full cause-and-effect picture so they can plan and implement (a) our Figma plugin bridge to the AI agent, (b) a design-reviewer agent based on the ready-for-dev checklist, (c) the pipeline that verifies animations in the browser.

The document is a brief, not a spec. Architectural decisions are intentionally left open where the consilium should make them at planning time.

---

## 1. The problem

When we receive Figma from a partner studio and try to generate code via Claude Code / Cursor + the Figma MCP, we hit three classes of problems.

**1.1. Hallucinated components.** The agent does not know `src/components/ui/button.tsx` already has a `<Button>`. It creates its own parallel `<Button>` with its own styles. Two button hierarchies grow in the codebase. Figma Code Connect solves this — but only on the **Organization plan ($55/editor/mo)** or Enterprise.

**1.2. Hallucinated layer names.** Layer names in Figma are literally turned into component / class / variable names. When the designer hasn't renamed `Frame 427`, the code receives `<Frame427>`, `.group-12`, `const rectangle89`. Unsupportable.

**1.3. Motion intent is fully lost.** The official Figma MCP does **not** expose prototype reactions. The Smart Animate spec (duration, easing, what moves) is invisible to the agent. The designer writes the animation in prose on a sticker → the agent doesn't parse the sticker → motion in the code is guessed.

On top of those three, there's a hand-crafted pain in preparing Figma "for dev". Every designer does it differently. There's no machine-checkable "ready-for-dev" contract. We don't have a tool that tells the designer "you have 14 frames with default names and no Auto Layout".

---

## 2. Solution in one sentence

Our own Figma plugin + a local MCP server + a design-reviewer agent — all running on the free Plugin API on any Figma plan, Professional included.

## 3. Why this approach

### 3.1. Why our own plugin, not Code Connect

| Parameter | Code Connect | Our plugin |
|---|---|---|
| Figma plan | Organization+ ($55/editor/mo) | Any, Professional included |
| Cost | ≈$3,300/yr for 5 editors | $0/yr |
| Setup | ~1 day | 3–5 dev-days |
| Architectural control | bound by Figma ToS | full |
| Can extract prototype reactions | indirectly via `get_design_context` | yes, directly via `node.reactions` |
| Can extend for our needs (animations, reviewer) | no | yes |

Ony is likely on Professional. Pitching them an upgrade to Organization solely for Code Connect is a commercial conversation we can sidestep.

### 3.2. Why `grab/cursor-talk-to-figma-mcp` as the base pattern

Open-source, 6.8k stars, active. Already implements:
- Figma plugin with UI + WS client
- Node.js WS relay (port 3055)
- MCP server with read+write tools (`get_design_context`, `get_local_components`, `get_annotations`, `set_instance_variant`, `set_annotation`, etc.)
- Reconnect via ping/heartbeat
- Channel ID routing

A fork is needed in order to (a) strip the write tools we don't need on pilot (risk reduction), (b) add `get_code_mapping`, (c) add `get_reactions` for animations.

### 3.3. Why our developer runs the plugin, not Ony's designer

The grab pattern originally assumes the designer opens the plugin in Figma and keeps the window open. That's undesirable for two reasons:
- Time coordination (timezones, distractions)
- Distribution: on Professional you cannot publish private plugins; we'd be left with either a public Community plugin (Figma review ~1 week) or shipping a local install to the designer.

**Better solution:** Ony adds our developer to the Figma file as `can_comment` (minimum) or `can_edit` (ideal). Our developer opens that file at home, runs the plugin at home, everything happens on his machine. Ony does its work as usual.

Side-effect: we get write access if `can_edit`. That's useful for the reviewer agent (see §6) — it can drop annotations / comments straight into Figma.

### 3.4. Why Playwright + Web Animations API for verifying animations

An LLM struggles to see a 4px shift in a screenshot. But it reads the string `"28px"` minus `"24px"` perfectly. So verification rides on numerical deltas, not on pixel-diff.

`element.getAnimations()` returns Animation objects with `effect.getTiming()` (duration, easing, fill, iterations) and a `finished` Promise. It's a standard browser API, vendor-library-free. We assert duration + easing to the millisecond.

Frame-by-frame: set `animation.currentTime = X * duration; animation.pause()` at multiple keyframes (0/25/50/75/100%), take screenshots, diff against frames extracted from the Figma prototype recording via ffmpeg.

### 4.1. Topology

```
│  │  • UI: channel ID + Connect button + status badge      │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────┬───────────────────────────────────┘

┌──────────────────────────▼───────────────────────────────────┐

│  │  WS relay (Node.js, port 3055)                         │  │

│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### 4.2. Data flow in normal mode (generate code from design)

1. Developer selects a frame in Figma, copies the node URL.
2. Asks Claude: "generate code for this frame".
3. Claude calls `get_design_context(nodeId)` → receives context (layout, tokens, components).
4. Claude calls `get_code_mapping(nodeId)` for each component in the tree — receives the canonical import + propMap. If the mapping is absent, it stops and asks the developer.
5. If the tree contains motion — Claude calls `get_reactions(nodeId)` → JSON `{trigger, actions, duration, easing, targetNodeId}`.
6. Claude generates JSX. Uses only imports from the mapping. Uses only Variables for tokens. Writes animations per reactions.
7. Starts the dev server. Through the Playwright MCP it verifies the result. If there is motion — a separate assertion `getAnimations()` against the spec.

### 4.3. Data flow in reviewer mode (see §6)

1. Developer / sales-architect runs: "review this Figma file".
2. Claude calls `review_node(rootId)` (or several times for different pages).
3. The MCP server tells the plugin to traverse the tree, collect all nodes with base meta (name, type, has-auto-layout, variables-used, annotations, etc.).
4. Claude applies rules from `./.figma/rules.json` (the ready-for-dev checklist in machine-readable form) to the collected tree.
5. Claude generates an HTML report with findings: `nodeId, severity, rule, what was found, how to fix`.
6. Optionally — writes annotations straight into Figma via `set_annotation` (if `can_edit`).

## 5. Data contracts

### 5.1. `./.figma/mapping.json` (substitute for Code Connect)

```json
{
  "figmaFileKey": "abc123",
  "components": {
    "1:23": {
      "figmaName": "Button/Primary/Large",
      "codePath": "src/components/Button.tsx",
      "import": "import { Button } from '@/components/Button'",
      "propMap": {
        "Variant=Primary":   { "code": "variant", "value": "primary" },
        "Variant=Secondary": { "code": "variant", "value": "secondary" },
        "Size=Lg":           { "code": "size",    "value": "lg" },
        "Disabled=true":     { "code": "disabled","value": true }
      },
      "slots": {
        "Icon":  { "code": "leftIcon" },
        "Label": { "code": "children" }
      }
    }
  }
}
```

Decisions the consilium must make:
- Keep the source of truth in `mapping.json` (repo) or in `sharedPluginData` on Figma nodes (in-file)? Hybrid: source in repo, mirror in plugin data for a "wired up" UI indicator.
- How to handle nested instances and `figma.children()` paths.
- Are transformation hooks needed (e.g., map `Variant=Default` to `variant=undefined`).

### 5.2. JSON anim spec (output of `get_reactions`)

```json
[
  {
    "nodeId": "1:42",
    "nodeName": "card/hover-trigger",
    "trigger": { "type": "ON_HOVER" },
    "actions": [
      {
        "type": "SMART_ANIMATE",
        "destinationId": "1:43",
        "duration": 0.24,
        "easing": {
          "type": "CUSTOM_CUBIC_BEZIER",
          "bezier": [0.4, 0, 0.2, 1]
        },
        "matchLayers": true,
        "deltas": [
          { "property": "scale", "from": 1.0, "to": 1.05 },
          { "property": "shadow", "from": "sm", "to": "lg" }
        ]
      }
    ]
  }
]
```

Field names mirror Figma `Reaction` / `Action` / `Transition` API verbatim (D-006 alignment). `Reaction.actions[]` is the modern form; deprecated singular `Reaction.action` handled as legacy fallback. Animation extraction only applies to `NODE`-type actions (others: BACK / CLOSE / URL / UPDATE_MEDIA_RUNTIME / SET_VARIABLE / SET_VARIABLE_MODE / CONDITIONAL — intent only, no motion).

Decisions for the consilium:
- `deltas` will have to be computed by comparing source and destination frames (Figma doesn't expose an explicit diff). Which property set we cover in iteration one.
- Spring presets (Gentle/Quick/Bouncy/Slow) and `CUSTOM_SPRING` (mass, stiffness, damping, initialVelocity) are exposed directly by Figma `Easing` API. 1:1 mapping to Framer Motion `transition={{type:'spring', mass, stiffness, damping}}` is possible without visual calibration.

### 5.3. `./.figma/rules.json` (ready-for-dev rules for the reviewer agent)

The schema must be extensible. Base idea:

```json
{
  "version": 1,
  "rules": [
    {
      "id": "naming.no-default-frame",
      "severity": "block",
      "category": "structure",
      "appliesTo": ["FRAME", "GROUP", "RECTANGLE", "TEXT"],
      "check": "node.name matches /^(Frame|Group|Rectangle|Text|Ellipse) \\d+$/",
      "message": "Default name {{name}}. Give it a semantic name.",
      "fix": "Rename in the form Section/Element or Component/Variant."
    },
    {
      "id": "layout.no-auto-layout",
      "severity": "block",
      "category": "structure",
      "appliesTo": ["FRAME"],
      "check": "node.layoutMode === 'NONE' && node.children.length > 1",
      "message": "Container with {{childCount}} children, no Auto Layout.",
      "fix": "Enable Auto Layout, set direction + gap + padding."
    }
  ]
}
```

Decisions for the consilium:
- Embedded DSL for `check`s (JSONLogic, JEXL, custom)?
- Can rules be executed safely in the plugin sandbox?
- Versioning of rules, backward compatibility.

## 6. The reviewer agent

### 6.1. Why we need it

So that Ony's designer gets automatic feedback against the checklist not from us by hand but from an agent. That (a) scales to new clients, (b) surfaces gaps in the checklist by the run itself (where the agent lies — we lock down a rule; where the agent is right but no rule existed — we add one), (c) becomes a product asset for sales.

### 6.2. First iteration's loop

```
1. Ony provides a Figma (a custom landing demo)
2. The reviewer agent traverses the frame, produces an HTML report
3. Ony's designer reads the report:
   • where the agent is right → fixes gaps in Figma
   • where the agent lies → we mark it so the agent stops doing that
4. Designer fixes Figma against the findings
5. The agent regenerates the page as code
6. We grow rules.json
7. Repeat on the next landing
```

Per iteration: rules.json grows, agent mistakes feed back into its system prompt, the checklist becomes practically verified rather than theoretical.

### 6.3. Why we demo on a custom design, not on Material / HIG / Liquid Glass

On finished design systems too many rules are covered implicitly by the system itself (named tokens, variant naming, etc.). The reviewer agent will find nothing. We need a living custom design with no ready-made system — that's where the real gaps show, and those gaps are the whole point.

### 6.4. What the reviewer checks in iteration one

Minimal set (everything from the ready-for-dev checklist we already agreed on):

- **Structure:** Auto Layout, sizing (Hug / Fill / Fixed), default names, slash notation, variants vs duplicate frames, hidden layers
- **Tokens:** raw hex / px vs Variables, three-tier consistency, modes for light/dark
- **Annotations:** present on interactive elements (hover / press / focus / disabled), motion (duration + easing) or a Loom reference
- **Breakpoints:** mobile + desktop present, tablet optional
- **Handoff:** one icon set, separate layer for heavy motion marked as such, Ready-for-Dev status

Each rule → a JSON object as in §5.3. Severities: `block` (cannot start without), `warn` (discussable), `avoid` (antipattern).

### 6.5. Report format

HTML with an interactive expand for each finding. Structure close to the existing brief:

```
[severity badge] [category] [rule id]
└── node: Frame 427 (id 1:23)
└── what was found: default name
└── why it matters: layer names become component names in code
└── how to fix: rename to Hero/Section or equivalent
└── link: open in Figma → https://figma.com/file/...?node-id=1:23
```

## 7. Distribution and access

### 7.1. Figma access

- Ony adds our developer to the Figma file as `can_comment` minimum, `can_edit` ideal.
- At the plan level Ony stays on Professional — no upgrade required.
- On our developer's side: Figma Desktop + plugin loaded via `Plugins → Development → Import from manifest`.

### 7.2. Plugin manifest

```json
{
  "name": "Effective ↔ Figma Bridge",
  "id": "effective-figma-bridge",
  "api": "1.0.0",
  "main": "code.js",
  "ui": "ui.html",
  "editorType": ["figma"],
  "networkAccess": {
    "allowedDomains": ["ws://localhost:3055"],
    "reasoning": "Local bridge to coding agent",
    "devAllowedDomains": ["ws://localhost:3055", "http://localhost:3055"]
  },
  "documentAccess": "dynamic-page"
}
```

### 7.4. Runtime requirement: Figma Desktop only (pilot)

`ws://localhost:3055` works inside Figma Desktop (which loads plugins over `http://`). It does NOT work in Figma web (https://) due to CSP mixed-content blocking. Pilot supports Figma Desktop only. If web support becomes a requirement post-pilot, add `wss://` with a self-signed cert workaround (manifest validation note: WSS with explicit port may fail validation; see `OQ-012`).

### 7.3. Distribution options (by maturity)

1. **Local install via manifest** — for the pilot, no publication needed.
2. **Community plugin (public)** — after a successful pilot, passes Figma review ~1 week. Worth it if we'll sell this as a process to other clients.
3. **Private organization plugin** — requires Org/Enterprise. Not our case for Ony.

## 8. Risk register

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| Figma changes Plugin API, breaks our fork | medium | medium | Pin a tagged release of grab, rebase quarterly. Cover the core path with integration tests. |
| Plugin dies when the file is closed | high (normal behaviour) | low | Plugin reconnects via ping/heartbeat. Long operations (the reviewer agent) are idempotent so we can restart. |
| Cross-file scan (the whole library) doesn't work from one plugin instance | high | medium | Use the Figma REST API for cross-file operations (works on any plan with a PAT). The plugin stays per-file. |
| Variant naming drift between Figma and mapping.json — silent break | high | high | CI gate: on every rebuild, verify consistency of mapping.json vs the actual variants in Figma. Alert on drift. |
| Spring presets don't map 1:1 to Framer Motion | ~~high~~ low | ~~medium~~ low | RESOLVED 2026-06-08: Figma `Easing` exposes mass/stiffness/damping/initialVelocity directly via `CUSTOM_SPRING`. 1:1 mapping possible. See D-006 / brief §5.2. |
| Ony's designer objects to "a plugin of ours on their file" by policy | low | high | At the kickoff explicitly state it's read-only by default. Write access (`set_annotation`) only with agreement. |
| Leakage of sensitive design through local logs | low | high | Don't log node content by default. Only id + meta. Log files in `.gitignore`. |
| Performance on large files (1000+ frames) | medium | medium | Streaming traversal. Depth/width limit. Pagination in the reviewer agent. |
| CVE in grab repo or its deps | low | high | Pin versions, security scan in CI, watch CVE feeds (CVE-2025-53967 in figma-developer-mcp set a precedent). |

## 9. Open questions for the consilium

1. **MCP transport:** stdio (classic Claude Code) or HTTP (needed for remote agents)? Support both?
2. **Mapping persistence:** file-only in repo, in-file only via `sharedPluginData`, or hybrid? If hybrid, who is the source of truth?
3. **DSL for rules.json:** JSONLogic, JEXL, custom, or JS functions executed in a sandbox? Trade-off between readability and flexibility.
4. **Concurrent agents on one file:** do we need to support several Claude sessions at once via a single WS relay? Complicates routing, simplifies UX.
5. **Reactions deltas:** compute the source/destination diff in the plugin (heavier, more accurate) or hand raw nodes to the agent (lighter, agent compares itself)?
6. **Reviewer output format:** HTML only, plus JSON for CI, plus annotations directly in Figma? All three?
7. **Hot reload:** mapping.json updated — should the MCP server reread automatically or require a restart?
8. **Auth:** is authentication between plugin and WS relay needed at all? Channel ID is routing, not security. Do we trust that localhost = ours?
9. **Cross-file via REST:** in which scenarios is it needed (library scan)? Where do we store the PAT?

## 13. Conversation context (for an agent coming in cold)

This document was produced in preparation for a one-hour meeting with the design studio Ony. Effective.dev and Ony are discussing a partnership: Ony designs, Effective writes code. Today (2026-06-08) we are agreeing on the Figma → Dev process.

Key tenets taken from the discussion:

- Figma's Code Connect is too expensive and gates on an Organization plan Ony doesn't have — we route around it with our own plugin
- Ony's designer should not have to keep anything open — Ony simply shares the file with our developer as `can_edit`, everything runs on our side
- Animations are a separate pain point, the official MCP doesn't expose them; our plugin pulls `node.reactions` directly
- The pilot is on a custom design, not on finished HIG/Material — otherwise the reviewer finds nothing
- The loop: reviewer agent → design review → rule expansion → rebuild → next iteration
- After a few iterations we end up with (a) a practically-verified checklist, (b) a trained agent, (c) a replicable process for new clients
